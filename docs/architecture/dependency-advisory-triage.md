# Remaining high dependency advisories

Review date: 1 October 2026. `pnpm audit --prod --json` reports zero critical, two high, one moderate, and seven low findings. Both high findings are infinite-loop denial of service advisories in `image-size@1.2.1`: malformed JXL/HEIF boxes and malformed ICNS entries. Patched 2.0.3 and 2.0.4 releases are published, but the transitive consumers here use the 1.x callable default-export API and no patched 1.x release exists. See [JXL/HEIF](https://github.com/advisories/GHSA-5p2g-fcmc-qvqq) and [ICNS](https://github.com/advisories/GHSA-w3rx-r6r6-pgpr).

| Dependency path | Actual use in this repository | Current exposure |
| --- | --- | --- |
| `pptxgenjs → image-size` in the API | PptxGenJS 4.0.1 declares the dependency, but its distributed JavaScript does not import `image-size`; its image-size helper is commented out. `FilesService.loadPresentationImages` reads uploaded images with Sharp, limits them to 25 million pixels, converts unsupported slide formats to PNG, and supplies explicit width, height, and data URI values to `slide.addImage`. | No call from presentation generation into the affected parser was found. Recheck if PptxGenJS or the presentation path changes. |
| `@react-three/fiber` and x402 peers → React Native → Metro → `image-size` in the API | Metro calls `image-size` from `metro/src/Assets.js`. The API's user project builder uses esbuild with `platform: 'browser'`; the API source does not import or invoke Metro. | Metro's asset parser is installed transitively but is not used for user project builds. Recheck if Metro is introduced as a runtime builder. |
| `fumadocs-core → image-size` in Docs | Fumadocs calls `image-size` from its MDX image plugin during compilation. `source.config.ts` limits Docs input to the repository's `content/docs` tree. The current tree has no Markdown image nodes; visitors cannot submit MDX for compilation. | A malicious committed image could hang a Docs build, while a visitor cannot send an image to this parser at runtime. Recheck if Docs gains user-generated content or remote image compilation. |

This review finds no current path from an untrusted Web/API request to either vulnerable parser. The package and two audit findings remain in the lockfile. Do not suppress the audit or substitute an unreviewed fork solely to clear the report. Re-run the audit and this reachability review before release and after changes to PPTX, project builds, or Docs content handling.

The remaining moderate finding is [unbound OAuth resource indicators](https://github.com/advisories/GHSA-p2fr-6hmx-4528) in `@better-auth/oauth-provider@1.6.22`, which runs in Commons Identity. The advisory states that a deployment with a single `validAudiences` entry cannot mint a token for a different audience. Commons Identity sets the single value `commons-platform`, and both the API gateway and API token verifier require that audience; the documented cross-audience escalation is therefore bounded in this configuration, while the resource-binding standards gap remains. The patched 1.7 line requires more than a package bump: this service has existing `oauthClient` rows, uses the removed `validAudiences` setting, writes the old `public` and `type` columns, and runs the standalone device authorization flow. Follow the [official 1.7 upgrade guide](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/guides/1-7-upgrade-guide.mdx): audit and migrate client rows, generate and review schema changes, update resource configuration and client registration, then exercise email, Google, CLI device login, authorization code, client credentials, refresh, and protected-resource checks against staging before deployment. The advisory remains open until that migration is complete.
